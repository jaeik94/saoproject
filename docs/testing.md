# 테스트와 측정 (Claude 작업 참고)

코드를 고치거나 수치를 측정할 때 따르는 방법이다. 규칙의 근거는 기획서, 임시값과 구현 해석은 `docs/decisions_combat.md`, 진행 상황은 `docs/progress.md`에 있다.

## 검증의 세 종류

| 종류 | 위치 | 묻는 것 | 결과 |
| --- | --- | --- | --- |
| 단위 테스트 | `tests/` | 규칙이 기획서대로 동작하는가, 같은 시드면 같은 결과인가 | 통과·실패 |
| 측정 도구 | `app/` (`tiers`, `builds`, `hunt`, `styles`, `aggro`, `batch`) | 수치와 플레이 방식이 의도한 모양인가 | 표와 수치. 판단은 기준과 비교해서 |
| 기획 검증 모델 | `design_models/` (아직 없음) | 코어에 없는 단계(하루 구조, NPC, 시장)의 기획 수치가 맞는가 | 가정값에 의존하는 추정 (CLAUDE.md 참고) |

셋을 섞지 않는다. 단위 테스트는 수치의 좋고 나쁨을 판정하지 않고, 측정 도구는 규칙의 옳고 그름을 판정하지 않는다.

## 실행

```
python -m unittest discover -s tests -t .           # 전체 테스트 (약 90개, 클라우드에서 약 13초)
python -m unittest tests.test_rules -v              # 한 파일
python -m unittest tests.test_rules.KinTest -v      # 한 클래스
```

- 코드를 고치기 전과 후에 전체 테스트를 돌린다. 고치기 전에 이미 실패하는 테스트가 있으면 먼저 알린다.
- 커밋 전에는 반드시 전체 통과.

## 테스트 작성 규칙

- **기획서 조항 하나에 테스트 하나 이상.** 테스트 이름이나 docstring에 어떤 규칙인지 적는다 (예: `test_first_hitter_after_rise_takes_aggro` = 무력화 기상 수색).
- **확률을 확정으로 만들어 규칙만 본다.** 데이터의 확률 값을 0 또는 10000으로 바꾼 사본으로 전투를 만든다 (`test_auto_defense.raw_data(auto_bp=...)`). 확률 분포 자체는 측정 도구의 일이다.
- **데이터 파일을 고치지 않는다.** `raw_data()`로 읽은 dict를 테스트 안에서 변형한다. 엔진 규칙을 시험하는 데만 필요한 공격은 테스트 파일 안에 정의한다 (`test_parry_knockdown.TEST_SWEEP` 등).
- **상태는 직접 세팅한다.** 칸, 방향, 체력을 정한 뒤 `run_until` 같은 도우미로 원하는 사건까지 진행한다 (`test_parry_knockdown.Base`). 규칙 단위 확인에는 코어 내부 메서드를 써도 된다 (`test_rules` 머리말).
- **임시 수치에 묶인 단언을 피한다.** "피해가 정확히 37"보다 "후면이 정면보다 크다", "넘어짐이 일어난다"처럼 관계와 발생 여부를 확인한다. 수치가 기획서에 확정돼 있을 때만 값을 단언한다.
- **결정론을 지킨다.** 새 실행 경로(새 도구, 새 전투 구성)를 만들면 `tests/test_determinism.py`에 "같은 시드 = 같은 로그" 케이스를 추가한다. 해시 시드가 달라도 결과가 같아야 한다.

### 하지 않는 것 (CLAUDE.md 작업 원칙)

- 실패하는 테스트를 끄거나, `skip`하거나, 기대값을 결과에 맞춰 고치지 않는다.
- 규칙이 바뀌어 기대값을 고쳐야 하면, 근거가 된 기획서 조항을 커밋 메시지에 적는다.
- 테스트를 통과시키려고 코어에 테스트 전용 분기를 넣지 않는다.

## 측정 도구

| 명령 | 보는 것 | 기준 |
| --- | --- | --- |
| `python -m app.tiers --n 100` | 적 등급별 1:1, 3:1 결과 (완벽 대처·단순·평타 봇) | `data/tiers.json` (사용자 정의 등급 기준) |
| `python -m app.builds --n 100 --bot perfect` | 무기 6종 × 적 1:1 | 무기 간 큰 편차가 없는가 |
| `python -m app.hunt --enemy <id> --kills 10 --n 50 --bot orig` | 연속 사냥 (체력 이어 감, 휴식 포함 1마리당 시간) | `docs/progress.md`의 목표 |
| `python -m app.styles --which elite --n 20` | 플레이 방식 비교 | 원작형이 강화 적에게 유리한가 (`progress.md` 원작 전투 원칙) |
| `python -m app.aggro --n 100` | 어그로 이동, 딜러가 노려진 시간 | `progress.md` |
| `python -m app.frames --enemy <id>` | 프레임표, 반격 창, 끊기·패리 가능 여부 | 프레임 설계 확인용 |
| `python -m app.batch ...` + `python -m analysis.summarize logs/<폴더>` | 임의 구성 여러 판 → 로그 요약 | 질문에 따라 |

- **봇은 화면에 보이는 정보만 쓴다** (`app/bots.py` 머리말). 결과가 이상하면 규칙보다 봇의 판단을 먼저 의심한다. 봇의 한계로 결과가 흐려지면 보고에 적는다 (예: `progress.md`의 "봇의 틈 판단이 규칙의 틈과 다름").
- 봇을 원하는 결과가 나오도록 비틀지 않는다. 봇은 사람이 할 법한 싸움법을 흉내 내는 비교 도구다.
- **표본**: 비교 판단은 `--n 100` 이상, 빠른 확인은 `--n 20`. 시드를 고정하고, 보고할 때 명령·n·시드를 함께 적는다.
- `logs/`는 git에 올리지 않는다. 결과는 `docs/progress.md`의 "최근 측정 요약"에 요약해서 남긴다.

## 측정 결과 보고 형식

1. 무엇을 확인하려 했는가 (질문 한 줄)
2. 실행한 명령과 조건 (n, 시드, 봇, 바꾼 데이터)
3. 결과 표
4. 기준(`tiers.json`, `progress.md`, 기획서)과 비교
5. 해석과 한계 (봇 판단, 표본, 임시값)
6. 다음에 바꿀 것 후보. 수치를 바꾸는 결정은 사용자와 정한다.

## 작업 순서 (클라우드 세션 포함)

1. `git pull`로 최신을 받는다. 클라우드 작업 공간은 시간이 지나면 사라지므로 작업은 항상 커밋으로 남긴다.
2. 전체 테스트를 돌려 출발점을 확인한다.
3. 코드·데이터를 고친다. 규칙을 바꾸면 테스트를 먼저 또는 함께 쓴다.
4. 전체 테스트를 돌린다.
5. 필요하면 측정 도구를 돌리고 위 형식으로 보고한다.
6. `docs/progress.md`(현재 작업, 최근 측정, 다음 할 일)와 `docs/decisions_combat.md`(새 임시값·해석)를 갱신한다.
7. 커밋하고 푸시한다.
